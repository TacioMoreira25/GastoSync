## Fluxo de OTP, Cadastro Pendente & Política de Senhas

- [ ] CHK001 - O fluxo de reenvio de código (`FR-002`) especifica um intervalo mínimo de espera (cooldown) entre reenvios para o mesmo e-mail e o comportamento esperado caso uma nova solicitação ocorra antes do término da janela? [Gap, Spec §FR-002, §Contract 1.3]
- [ ] CHK002 - Os requisitos tratam de forma explícita e consistente o cenário de novo cadastro com e-mail pendente de verificação, definindo se nome e senha anteriores são sobrescritos, qual código de resposta HTTP é retornado e o que acontece com tentativas acumuladas do OTP anterior? [Ambiguity, Spec §Edge Cases, §Contract 1.1]
- [ ] CHK003 - A política de senha forte (`FR-004`) documenta nos requisitos funcionais o limite máximo de caracteres, o tratamento de espaços nas extremidades e o conjunto explícito de caracteres especiais aceitos? [Clarity, Spec §FR-004]
- [ ] CHK004 - Os requisitos deixam claro se o bloqueio de contas com `email_verified = false` (`FR-003`) impede também o uso local offline no dispositivo móvel ou restringe-se exclusivamente à autenticação e sincronização com a nuvem? [Ambiguity, Spec §FR-003, Constitution §I]
- [ ] CHK005 - A supressão do campo `dev_preview_code` fora de desenvolvimento/teste (`Contract §1.1`, `Assumptions`) está formalizada como requisito obrigatório de segurança (incluindo comportamento quando provedores de e-mail falham em produção) e não apenas como nota informativa? [Gap, Security, Spec §Assumptions, Contract §1.1]
- [ ] CHK006 - A premissa de retrocompatibilidade para contas previamente existentes e conta de demonstração (`Assumptions`) define objetivamente o critério de elegibilidade (ex.: data de corte da migração) e se senhas antigas fora da nova política permanecem válidas no login? [Assumption, Edge Case, Spec §Assumptions, §FR-004]

## Isolamento Multi-Tenant, Precisão Monetária & Integridade de Dados

- [ ] CHK007 - A lista de tabelas com isolamento por `user_id` e `ON DELETE CASCADE` em `FR-007` está consistente com `FR-019` e o modelo de dados (`credit_cards`, `password_reset_tokens`, `email_verification_tokens`), eliminando a omissão de entidades persistidas em nuvem? [Conflict, Spec §FR-007, §FR-019, Data Model §1.1–1.7]
- [ ] CHK008 - O requisito de precisão decimal exata sem erro de arredondamento (`FR-006`, `SC-002`) está consistente com a modelagem local que define colunas `RealColumn` (ponto flutuante) no armazenamento do dispositivo (`Data Model §2.1–2.3`), explicitando a regra de arredondamento ou escala em centavos antes da persistência e sincronização? [Conflict, Spec §FR-006, §SC-002, Data Model §2.1–2.3]
- [ ] CHK009 - Os requisitos de ciclo de vida e remoção em cascata (`Research §Decision 1`) estão consistentes com a ausência de chave estrangeira nas tabelas de OTP baseadas em `email` (`Data Model §1.2–1.3`, `Tasks §T003`), especificando como tokens órfãos ou expirados são expurgados quando uma conta é removida? [Conflict, Research §Decision 1, Data Model §1.2–1.3]
- [ ] CHK010 - O isolamento local por `userEmail` (`FR-009`) inclui explicitamente todas as tabelas multi-conta do dispositivo (incluindo `LocalCreditCards`) e define a regra de atribuição/migração de registros pré-existentes sem e-mail associado na transição para o Schema v3? [Ambiguity, Gap, Spec §FR-009, Data Model §2.3–2.4]
- [ ] CHK011 - Os requisitos de sincronização com `client_uuid` e `local_id` (`FR-008`, `Data Model §1.4–1.5`) definem de forma determinística a política de resolução de conflitos em caso de edição concorrente entre múltiplos dispositivos ou colisão de identificadores legados? [Gap, Spec §FR-008, Data Model §1.4–1.5]
- [ ] CHK012 - Os requisitos de exclusão lógica (`deleted_at` em `FR-008` e `US4 §3`) especificam janela de retenção/expurgo definitivo (conformidade e privacidade), validação obrigatória de titularidade (`user_id`) e precedência entre uma exclusão e uma edição offline concorrente? [Gap, Edge Case, Spec §FR-008, §US4]

## Controle de Acesso, Rate Limiting & Proteção de Segredos

- [ ] CHK013 - Os requisitos de limitação de requisições contra força bruta (`FR-005`) quantificam na especificação os limiares por janela (ex.: `20 req/min` do Contrato), cobrem de modo consistente o endpoint de login (`Contract §1.4` vs `Spec §FR-005`) e definem o comportamento por IP real atrás de proxy reverso ou redes móveis compartilhadas (NAT)? [Clarity, Conflict, Spec §FR-005, Contract §1.1–1.4]
- [ ] CHK014 - O comportamento após atingir 5 erros consecutivos no OTP (`FR-001`, `Edge Case`) especifica se o usuário pode solicitar novos códigos indefinidamente logo após o bloqueio ou se há limite máximo de reemissões e janela de bloqueio progressivo por conta? [Ambiguity, Edge Case, Spec §FR-001, §Edge Cases]
- [ ] CHK015 - A proibição de coleta, armazenamento e tráfego de dados bancários sensíveis em cartões (número PAN, CVV, validade e senha) está documentada como requisito funcional/de segurança normativo (`FR-019`) em vez de constar apenas na narrativa de User Story e decisões de pesquisa? [Gap, Traceability, Spec §US5, §FR-019, Research §Decision 6]
- [ ] CHK016 - Os requisitos de gestão de sessão (`Constitution §VI`) especificam de forma mensurável a duração máxima do token JWT ("curta/média duração"), o comportamento esperado quando o usuário redefine a senha ou tem a sessão expirada e os requisitos de armazenamento seguro do token em Mobile vs Web? [Ambiguity, Gap, Constitution §VI]
- [ ] CHK017 - Os requisitos definem que o encerramento de sessão (`logout`) ou a troca de conta no mesmo dispositivo invalida caches, streams em memória, notificações pendentes e histórico de chat da sessão anterior antes de carregar a nova conta? [Gap, Security, Spec §US4, §FR-009, §SC-005]

## Exceções, Recuperação de Falhas & Critérios Mensuráveis

- [ ] CHK018 - Estão definidos requisitos de recuperação e preservação de dados caso a migração de banco em nuvem (`NUMERIC(14,2)`) ou local (`Drift Schema v3`) encontre registros legados fora das novas constraints (ex.: `amount <= 0` ou valores nulos) ou falhe parcialmente? [Gap, Recovery, Data Model §1–2]
- [ ] CHK019 - Os requisitos especificam o comportamento transacional e a mensagem ao usuário quando todos os provedores de e-mail configurados (`Brevo`, `Resend`, `SMTP`) estão indisponíveis durante o cadastro ou reenvio de OTP (ex.: se o cadastro pendente é mantido ou revertido e se há fallback permitido)? [Gap, Exception Flow, Spec §Assumptions, §FR-001]
- [ ] CHK020 - O critério de aceitação `SC-001` ("concluído em menos de 90 segundos") define de maneira mensurável a fronteira temporal avaliada (se exclui atraso de entrega de provedores externos de e-mail e considera apenas processamento da API/interface)? [Measurability, Spec §SC-001]
- [ ] CHK021 - O critério `SC-005` e o requisito da auditoria de segurança (`FR-018`) estabelecem critérios objetivos de aprovação/bloqueio (níveis de severidade aceitáveis, escopo explícito entre cliente, API core e agente IA, e gatilho para reauditoria após mudanças pós-release)? [Measurability, Gap, Spec §FR-018, §SC-005]
