## Máquina de Estados de Boletos, Baixa Automática & Recorrência

- [ ] CHK001 - Os requisitos da máquina de estados de boletos (`FR-010`, `Data Model §3`) especificam objetivamente o critério de transição automática de `pending` para `overdue` (incluindo fuso horário de referência e atualização na virada do dia) e se a edição de um boleto `overdue` para uma data futura deve retorná-lo a `pending`? [Gap, Ambiguity, Spec §FR-010, Data Model §3]
- [ ] CHK002 - As regras de edição e exclusão (`FR-013`, `FR-011`) definem o comportamento esperado sobre boletos já liquidados (`status = 'paid'` com `linked_tx_uuid`), explicitando se o registro permanece imutável, se exige estorno ou se atualiza/remove em cascata a transação gerada na baixa? [Gap, Exception Flow, Spec §FR-011, §FR-013]
- [ ] CHK003 - O requisito de ajuste para recorrência no dia 31 (`Spec §Edge Cases`) define se os meses subsequentes (ex.: março após fevereiro dia 28/29) devem restaurar o dia âncora original (`31`) ou permanecer na data ajustada (`28`/`29`), e se há metadado documentado para preservar o dia âncora? [Ambiguity, Edge Case, Spec §Edge Cases, Data Model §1.5]
- [ ] CHK004 - Os requisitos de boleto recorrente (`FR-011`, `Data Model §3`) especificam se a próxima competência gerada na baixa de um boleto atrasado é calculada como `+1 mês` sobre a `due_date` vencida ou sobre a data corrente do pagamento? [Ambiguity, Edge Case, Spec §FR-011, Data Model §3]
- [ ] CHK005 - Os requisitos para o campo opcional de código de barras / PIX (`FR-010`, `FR-013`) definem limites de tamanho, regras de normalização/sanitização de entrada e o comportamento de estado vazio quando o boleto é cadastrado sem código copiável? [Clarity, Gap, Spec §FR-010, §FR-013]
- [ ] CHK006 - As restrições de categorias entre tipos de lançamento (`Data Model §1.4`: despesa nunca pode ser `'Renda'`) estão especificadas de modo consistente para criação e edição de boletos (`FR-010`, `FR-013`) e para geração automática de despesa na baixa (`FR-011`)? [Consistency, Gap, Spec §FR-010, §FR-011, Data Model §1.4]

## Cobranças Embutidas no Cartão (`is_credit_card_charge`) & Regras Contábeis

- [ ] CHK007 - A regra de dedução proporcional da fatura (`FR-011b` item c) define de maneira inequívoca como o sistema identifica qual lançamento representa o "lançamento geral da Fatura do Cartão" (por categoria, vínculo `credit_card_uuid` ou múltiplos cartões/faturas no mês) e como tratar o saldo caso a soma das assinaturas vinculadas exceda o valor da fatura? [Ambiguity, Gap, Spec §FR-011b, Research §Decision 3]
- [ ] CHK008 - Os requisitos tornam explícito se a confirmação mensal de um item com `is_credit_card_charge = true` deve apenas alterar `status` para `paid` (gerando o próximo mês se `is_recurring = true`) sem inserir entrada em `transactions`, e como itens já pagos com essa flag compõem os gráficos por categoria no mês vigente? [Ambiguity, Consistency, Spec §FR-011, §FR-011b, Tasks §T013]
- [ ] CHK009 - Os requisitos contábeis esclarecem de forma consistente como as 9 métricas financeiras (`Constitution §IV`), o Saldo Disponível e os totais de resumo em Transações tratam compras individuais com `payment_method = 'Crédito'`, pagamentos de fatura (`payment_method = 'Boleto'`) e itens `is_credit_card_charge = true` sem risco de dupla contagem? [Consistency, Gap, Spec §FR-011b, Constitution §IV]
- [ ] CHK010 - Está definido nos requisitos o comportamento para contas sem lançamentos realizados no mês atual (`transactions.isEmpty` ou renda zero) no cálculo do Score de Saúde Financeira e indicadores contábeis, evitando exibição de scores ou classificações fictícias? [Gap, Edge Case, Constitution §IV]

## Gestão de Cartões de Crédito & Faixa Saudável (50%–80%)

- [ ] CHK011 - Existe alinhamento documentado entre a especificação (`FR-019`) e a lista de tarefas (`Tasks §T029`) quanto ao estado inicial de cartões de uma nova conta (iniciar com zero cartões cadastrados pelo usuário vs. criação automática de cartão padrão)? [Conflict, Spec §FR-019, Tasks §T029]
- [ ] CHK012 - Os requisitos de `FR-020` e `US5` definem o comportamento de validação e fluxo alternativo quando o usuário registra uma compra com `payment_method = 'Crédito'` ou `is_credit_card_charge = true` e não possui nenhum cartão cadastrado? [Gap, Exception Flow, Spec §FR-019, §FR-020]
- [ ] CHK013 - A faixa saudável de uso do cartão está consistente entre `US5`, `FR-019` (`50%` a `80%`) e `FR-020` ("teto saudável (70%–80%)"), eliminando ambiguidade sobre qual limite percentual dispara o aviso preventivo, o alerta na Central de Notificações e o cálculo de margem saudável disponível? [Conflict, Ambiguity, Spec §US5, §FR-019, §FR-020]
- [ ] CHK014 - Os requisitos de cadastro de cartão (`FR-019`, `Data Model §1.7`) explicitam todas as regras de invariância de domínio: `limit_amount > 0`, `0 <= target_min_percent <= target_max_percent <= 100`, `due_day` entre `1` e `31` e unicidade (ou múltiplas seleções) da flag `is_primary`? [Completeness, Spec §FR-019, Data Model §1.7]
- [ ] CHK015 - O cálculo de utilização mensal do cartão (`US5 §3`, `Research §Decision 6`) especifica com clareza se o período considerado segue o mês-calendário (`1º ao último dia`) ou o ciclo móvel definido pelo `due_day` de vencimento, e se inclui apenas itens confirmados ou também assinaturas pendentes no mês? [Ambiguity, Spec §US5, §FR-020, Research §Decision 6]
- [ ] CHK016 - Os requisitos cobrem o tratamento de compras no `Crédito` sem vínculo de cartão (`credit_card_uuid = NULL`) e o efeito da exclusão lógica (`deleted_at`) de um cartão que já possua transações ou cobranças `is_credit_card_charge` associadas? [Gap, Edge Case, Spec §FR-020, Data Model §1.4–1.5, §1.7]
